# v0.14.0 Code + Security Review — 2026-07-12

Scope: `d328588..HEAD` — migration 14 (federated org structure: teams/projects/
memberships converge across nodes), ops/maintenance tooling, and the
`agent-memory update` self-updater.

Method: 6 parallel review agents (3 security lenses — sync/bundle, web/update,
ACL data core; 3 correctness lenses — db org core, sync+client, cli+update),
each returning findings independently; every finding then verified against
source before fixing. All fixes landed with regression tests
(`tests/test_review_fixes_v0_14.py`, plus updates to `test_teams_projects.py`
and `test_update_restart.py`). Suite: **273 passed**.

## The root cause

Migration 14 added org-structure records (team/project/membership,
org-tombstones) to the v3 sync bundle, but the merge path was written **without
porting the `trusted`/provenance model that already guards memory merges**. So
every org record was applied fully trusted — the single defect behind the three
most severe findings.

## Findings & resolutions

### H1 — CRITICAL: untrusted peer could forge team/project membership → ACL escalation
`sync.py` `_merge_team`/`_merge_project` ran with no trust check. A semi-trusted
(`shared`/`team:`/`project:`) — or an anonymous HTTP push — peer could send a
`team` record replacing a team's member set with attackers, and membership is
the authoritative ACL source (`_append_acl_filter`), so the attacker's agent
would then read that team's memories.
**Fix:** threaded an `org_scope` authorization through `import_bundle` →
`_merge_team`/`_merge_project`/`_apply_org_tombstone`. A peer may only assert
org records within its policy scope (`full` → any; `team:X` → team X + its
projects; `project:P` → only P; `shared`/anonymous → none). Rejected records are
counted in `stats["org_records_rejected"]`.

### H2 — CRITICAL: org-tombstone griefing + permanent takeover via future timestamps
An untrusted `org_tombstone` could delete teams/projects and strip visibility
grants off memories; and LWW had no upper time bound, so a `9999-…` timestamp
won every conflict forever and could never be corrected.
**Fix:** org tombstones are gated by the same `org_scope`; and
`_ts_too_future()` rejects any org `updated_at`/`deleted_at` more than 300s
beyond now (also counted as rejected).

### H3 — HIGH: `update` re-executed a `ps`-derived command line (local code exec / root escalation)
`_restart_web_process` SIGTERM'd and `Popen`'d an argv parsed from `ps` output.
A local process named `agent-memory-web` would be re-executed by the updater —
as root under `sudo agent-memory update`.
**Fix:** the web console now writes `<home>/web.pid` with its own pid + a
self-authored relaunch argv (`pidfile.py`). `_restart_web_from_pidfile` only
signals the recorded pid (verified alive) and relaunches the argv the console
wrote about itself — never a `ps` string. `ps` is still used for *reporting*
stale processes (no exec). Added a post-relaunch liveness check.

### H4 — HIGH: equal-timestamp org member sets diverged permanently
Unlike memory merges (which tie-break on content), org merges skipped on an
equal `updated_at`, so two nodes editing a team in the same second each kept
their own member set forever.
**Fix:** `_org_member_wins()` deterministic tie-break — on an equal timestamp
the lexicographically-greater sorted member set wins, so both nodes converge.

### H5 (db) — HIGH: orphan cleanup destroyed owner-readable memories (data loss)
`find_orphan_memories` ignored owner reachability and treated empty-but-existing
scopes as orphans, so `delete_orphan_memories` could permanently delete a live
agent's own memory.
**Fix:** a memory is an orphan only if its owner is not a live agent AND every
`team:`/`project:` grant points at a scope that no longer **exists** (deletion,
not emptiness). Existence — not membership count — is the gate.

### M1 — subset invariant diverged on import
`_merge_team`'s member REPLACE didn't cascade to `project_members`, leaving
project members who were no longer team members.
**Fix:** after replacing the team roster, drop project members not in it.

### M2 — a `shared` peer received the whole org membership graph (disclosure)
**Fix:** `include_org=False` for `shared`/unknown policy; org records export only
for `full`/`team:`/`project:`.

### M3 — project-scoped export leaked the full parent-team roster
**Fix:** for `project:P` export, the parent team record's members are narrowed
to the project's members (subset-safe, no leak).

### M4 (db) — member-removal cascade touched all projects, risking clobber
`_remove_team_member_row` bumped `updated_at` on every team project, not just
the ones the agent was in, which could overwrite a concurrent peer's real edit.
**Fix:** only the projects the agent actually belonged to are touched.

### M5 — deleting a team didn't strip the legacy bare-`team` grant (id-reuse resurrection)
`_strip_visibility_grant("team:X")` misses the bare-`team` + `source.team_id`
scheme, so a reused team id could resurrect read access.
**Fix:** `delete_team` also calls `_strip_bare_team_grant(team_id)`.

### M6 — destructive `orphans/delete` had no confirmation
**Fix:** `POST /api/maintenance/orphans/delete` now requires `?confirm=orphans`,
matching `purge_owner`; the WebUI button sends it.

### M7 — forgeable audit attribution
`MemberRequest.actor` was client-supplied and written to `org_audit`.
**Fix:** web membership changes record the fixed channel actor `"web"`; the
request field is accepted for compatibility but ignored.

### cli (M) — Windows service not detected; restart liveness
`_web_service_installed` had no win32 branch; restart reported success on Popen.
**Fix:** win32 branch queries `schtasks`; restart confirms the new process
stayed up.

## Residual / documented limitations (not bugs)

- **30s cross-process ACL cache window.** A membership change made in another
  process is reflected within the 30s TTL, not instantly. Acceptable, documented
  tradeoff (`_append_acl_filter` comment); a generation counter is a possible
  future tightening.
- **Revocation to an excluded node.** Removing a member propagates to remaining
  nodes; a node cut out of a scope's bundle delivery does not receive a targeted
  retraction of already-synced memory. This is inherent to a pull-based mesh over
  a single shared token and is documented in the user guide.
