# Code Review & Security Review — v0.13.0 (Teams & Projects)

Date: 2026-07-11 · Scope: `git diff v0.12.1..HEAD` (the teams/projects
milestone — schema/ACL/sync/endpoints/CLI/UI, ~626 changed lines) · Method:
three parallel review agents (teams/projects ACL security, db membership
correctness, web+CLI+UI), each returning verified findings; every
high-confidence finding was manually confirmed against source and fixed.

## Verdict

**The core ACL is sound.** The security reviewer confirmed the `project:<id>`
resolution is fully parameterized and only grants for projects the requester
actually belongs to; membership cascades run in the same transaction; every
membership write invalidates both caches; `_reconcile_agent_teams` and the
migration-13 backfill are correct; no SQL injection. Five real defects around
the edges were found and fixed (below), each pinned with a regression test.
238 tests pass; validation harness PASS.

## Fixed

**R1 · `create_project` could silently break the subset invariant (High)** —
the `ON CONFLICT` clause reassigned `team_id`, so recreating a project under a
different team left members who weren't in the new team. **Fix:** recreating a
project under a different team is rejected; `ON CONFLICT` updates only `name`.

**R2 · A metadata-only `register_agent` wiped memberships (Medium)** —
`teams=None` was treated as `teams=[]`, so editing an agent's display name (or
re-registering without teams) reconciled its membership to empty and cascaded
it out of every project. **Fix:** `teams=None` now leaves membership untouched;
only an explicit list reconciles. The web `AgentRequest.teams` is optional and
the Agents-tab form omits it when blank, so editing a name never wipes
Teams-tab-managed membership.

**R3 · Project sharing was unreachable via the web API (Medium)** —
`ShareRequest` and the `/share`·`/revoke` routes lacked `to_project`, so a
`project:<id>` grant couldn't be made from the API/UI. **Fix:** added
`to_project` end to end.

**R4 · CLI leaked raw tracebacks on domain errors (Medium)** — a subset
violation or missing team/project raised through `main()` (which had only a
`finally`), printing a Python traceback. **Fix:** `main()` catches
`ValueError`/`KeyError` → friendly `error: …` message + exit code 2.

**R5 · Deleting a team/project didn't revoke its visibility grant (Medium,
security)** — memories kept `visibility: ["team:X"]` / `["project:P"]` after the
team/project was deleted, so reusing the (human-chosen, reusable) id resurrected
read access for a new, unrelated group. **Fix:** `delete_team`/`delete_project`
strip the orphaned grant from every memory (reverting it to its remaining
grants, or owner-private) — an ACL-only change that doesn't touch `updated_at`.

## Confirmed clean (no action)

- `project:<id>` ACL clause: parameterized, appended only for the requester's
  actual project memberships (mirrors the team clause).
- Cascades: `_remove_team_member_row` removes the agent from the team's
  projects in the same transaction; `remove_agent` clears both membership tables.
- Cache invalidation on every membership write path; 30s TTL for cross-process.
- Migration-13 backfill: coerces with `str().strip()` + `INSERT OR IGNORE`,
  idempotent, safe on empty DBs.
- All new SQL parameterized; web routes under `/api/` (token-gated) and take
  the shared lock; WebUI renders via `el()`/`textContent` (no XSS); the project
  member picker offers only team members; i18n present in all 5 locales.

## Known design gaps (acknowledged, tracked separately — not defects)

- **Org structure isn't synced between nodes** — teams/projects/memberships are
  node-local; cross-node ACL correctness depends on consistent per-node
  definitions. Scheduled as the next milestone (federate the org structure).
- **Revocation doesn't retract already-synced memory** from a peer that already
  received it; peer policy isn't auto-coupled to local membership.
- **Membership changes are not audited.**
