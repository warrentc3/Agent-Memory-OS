# v1.0.0 Final Code + Security Review — 2026-07-12

Scope: `bc2608c..HEAD` — the v1.0 hardening batch after the v0.14 review (ACL
clock for share/revoke propagation, observability endpoints, resilience/backup
rotation, and the WebUI batch). Method: 2 parallel review agents (security lens
on the ACL clock + auth surface; correctness lens across the whole batch), each
finding verified against source before fixing. All fixes shipped with regression
tests; suite **302 passed**.

## Findings & resolutions

### F1 — HIGH (security): untrusted ACL merge could escalate visibility
The new independent-ACL-clock merge in `sync.py:_merge_memory` ran
unconditionally — ignoring `trusted`. A semi-trusted peer (or an anonymous push)
could re-classify a memory it had legitimately received as `team:X` into
`global` with a far-future `acl_updated_at`, permanently defeating the owner's
revoke. Same class of bug the org-record gating fixed, reintroduced in the ACL
path. **Fix:** the ACL merge now (a) rejects a future `acl_updated_at`
(`_ts_too_future`), and (b) from an untrusted peer accepts the incoming
visibility only if it is a SUBSET of the existing set (`_acl_change_allowed`) — a
revoke shrinks and propagates, an escalation is refused; trusted imports converge
freely. Regression: `test_untrusted_peer_cannot_escalate_visibility`,
`test_untrusted_peer_revoke_still_shrinks`.

### F2 — HIGH (data loss): `backup --keep` could delete the live database
`_rotate_backups` derived the rotation prefix by stripping trailing digits, so a
dest like `mem-2026-07-12.db` yielded prefix `mem` and `glob('mem*')` matched the
live `memories.db` — which could then be unlinked. **Fix:** rotation now excludes
the live DB and its WAL/SHM by name (hard backstop) AND requires the character
after the prefix to be a separator or digit, so a name-prefix collision is never
matched. Regression: `test_rotate_backups_never_deletes_live_db`,
`test_rotate_backups_prefix_series_memories_dash`.

### F3 — HIGH (correctness): `update_memory` didn't bump the ACL clock
A share/revoke performed via `update_memory(visibility=…)` (as opposed to
`_set_visibility`) left `acl_updated_at` untouched, so the change did not
propagate over sync — reopening, for that path, exactly the hole the ACL clock
closed. **Fix:** `update_memory` bumps `acl_updated_at` (microsecond resolution)
whenever `visibility` is in the changed fields. Regression:
`test_update_memory_visibility_propagates`.

### F4 — MEDIUM: archive/restore lost the ACL clock
`restore_archived` re-inserted without `acl_updated_at` (NULL → COALESCE to
`now`), which could clobber a peer's more-recent revoke on the next sync.
**Fix:** restore seeds `acl_updated_at` to the memory's `created_at` — a stable
floor that defers to any peer ACL decision made after creation (the safe
direction). Regression: `test_restore_archived_seeds_acl_clock`.

### F5 — LOW: `/metrics` could 500 a scraper
Unlike `/healthz`, `/metrics` had no guard. **Fix:** wrapped in try/except,
returning `503` with a comment line on error so a scrape degrades gracefully.

### F6 — LOW: read-only banner was dead-wired
The `#ro-banner` element and its i18n existed but nothing showed it. **Fix:** the
`api()` helper reveals the banner the first time a mutation returns `403` with a
read-only detail, so a read-only-token user gets a clear "changes are disabled"
notice.

## Confirmed clean (by the reviewers)

- Read-only middleware: no mutating route served over a safe method; `compare_digest`
  used correctly; empty/None RO token cannot authorize.
- `/api/maintenance/update-run`: fixed argv, real confirm gate, full-token only.
- Pidfile restart: argv only from the console's self-written pidfile, list-form
  `Popen`, live-same-user pid gate — no `ps` trust, no shell.
- Read-only token file: unchanged 0600 atomic-write discipline.
- `usage_summary`: set-based, no double counting; ACL microsecond tie-break holds.
